# Tuning, previewing and evaluating an expressive robot face (for Frank)

Scope: how teams preview, record/replay, live-tune, author by puppeteering, measure servo response, evaluate expressions with small samples, and make the stack safe. Researched 2026-10-30. Project context checked locally: `frank/web.py` already serves a localhost page with the stdlib `http.server.ThreadingHTTPServer`, and its `uv run` line already pulls in `websockets` and `mediapipe` (see `C:\Users\Lars Langenbach\Desktop\Halloween Animatronic\frank\web.py`, lines 4 and 34), so a browser-plus-WebSocket tool and a MediaPipe capture tool add no new dependency families.

Source-quality note: several facts below come from search-engine extracts of pages that could not be fully fetched (rate limits on bottango.com, PDF text not extractable). Those are marked "(search extract)". Vendor/SEO pages (kpower.com) are flagged where used.

## 1. Previews of a servo face without hardware: what exists, what fidelity is enough, what does not transfer

### Takeaway
The professional pattern (Engineered Arts, Furhat) is a virtual twin driven by exactly the same control values and timeline as the real robot, used for authoring and prototyping, with the real head kept for final confirmation. For a hobby-servo head, a cheap preview driven by the same joint angles (2D schematic or three.js/PyVista from the existing STLs) is enough to tune timing, blends and sequencing; it cannot show silicone-skin damping and drag, servo lag/deadband, or backlash, which must be modelled crudely (a lag filter) and confirmed on the head.

### Cited Findings
- Engineered Arts' Tritium Animator is a tool "for key-framing movements over time to create a sequence that runs on a robot"; it opens from the Tritium UI and its 3D view plays back on an SDF model of the robot; a "Limit Control" setting restricts which body parts a clip drives (search extract) — [EA docs: Tritium UI Animator](https://docs.engineeredarts.co.uk/guide/reference/software/tritium_ui_animator)
- EA glossary: clips are assets built from a set of Controls, each following a Curve through Keyframes; a Timeline is a linear sequence where track items are independently editable but combine into one result on playback (search extract) — [EA docs: glossary](https://docs.engineeredarts.co.uk/guide/glossary)
- EA Virtual Robot is a browser-based content tool; its timeline has a Motion Item (robot animation) plus audio and speech items; sequences can be set to Limit Control, be exclusive, or loop; all EA robots ship with a basic Virtual Robot account (search extract) — [EA wiki: Virtual Robot](https://wiki.engineeredarts.co.uk/Virtual_Robot)
- Virtual Robot animations can be called from Python or via a RESTful API; Ameca Gen 2 runs on Tritium 3, Gen 1 on Tritium 2 (search extract) — [EA wiki: Ameca](https://wiki.engineeredarts.co.uk/Ameca)
- Furhat: the SDK includes a virtual robot that "supports many of the real robot's features"; FaceCore and the Furhat Library are accessible for the virtual robot; it is used to prototype interactions and teleoperate (search extract) — [Furhat SDK](https://www.furhatrobotics.com/furhat-sdk)
- Furhat's newer face engine is built on Unity and ARKit — [Furhat latest software release](https://furhatrobotics.com/latest-software-release/)
- The Furhat Remote API can run against the virtual robot on localhost; supports named gestures (e.g. `furhat.gesture(name="ExpressDisgust", blocking=True)`) and custom gestures passed as frame dictionaries with timings and parameters — [PyPI furhat-remote-api 0.3](https://pypi.org/project/furhat-remote-api/0.3/)
- Disney Research "Physical Face Cloning" (SIGGRAPH 2012): measured elastic properties of candidate silicone skin materials, captured target 3D expressions, then optimized both the skin shape and the actuation parameters to best match targets; validated by fabricating skins for an articulated robot head — [Disney Research: Physical Face Cloning](https://la.disneyresearch.com/publication/physical-face-cloning/); [paper PDF (MIT CDFG)](https://cdfg.mit.edu/assets/files/Bickel_118-0371_compressed.pdf)
- Blender Servo Animation add-on (Tim Hendriks): servos are armature bones, each with Servo Settings; live mode sends positions in real time over Serial (UART/USB) or Web socket (TCP); README cites 16 servos at 60 fps running smoothly at 115200 baud; IK supported to compute several servo positions; licence GPL-3.0; latest version requires Blender 4.2 or higher — [GitHub: timhendriks93/blender-servo-animation](https://github.com/timhendriks93/blender-servo-animation)
- Companion Arduino library BlenderServoAnimation (with a LiveStream class and a web-socket live-mode example) — [GitHub: blender-servo-animation-arduino](https://github.com/timhendriks93/blender-servo-animation-arduino); [Arduino library reference](https://reference.arduino.cc/reference/en/libraries/blenderservoanimation)
- three.js `urdf-loader` (gkjohnson): ships a JS loader and a `URDFViewer` web component that renders the model in a THREE.js scene; joints are Object3D subclasses with lower/upper limits, values in radians; mimic joints supported (multiplier, offset); `loadMeshCb` lets you plug in an STL or other mesh loader — [urdf-loaders docs](https://gkjohnson.github.io/urdf-loaders/javascript/); [npm urdf-loader](https://npmjs.com/package/urdf-loader)
- A community React/three.js URDF viewer supports STL and DAE meshes with slider controls for all movable joints (small project) — [GitHub: qkrdkwl9090/urdf-viewer](https://github.com/qkrdkwl9090/urdf-viewer)
- PyVista slider pattern: `add_slider_widget` with a callback that receives the value and regenerates/updates geometry; a class-based callback can drive one mesh from several sliders, updating in place with `copy_from` — [PyVista: slider bar widget](https://docs.pyvista.org/version/stable/examples/03-widgets/slider-bar-widget.html); [PyVista: multiple slider widgets](https://docs.pyvista.org/examples/03-widgets/multi-slider-widget)
- What the skin does (Nikola android, Sato et al. 2022): silicone skin lacks human-like elasticity so natural wrinkles are difficult; AU 6 and AU 7 were hard to tell apart; AUs 9, 17 and 23 were not built "owing to the technical limitations of the silicone skin"; some AUs did not reach maximum intensity and overall expression intensity was weaker than human, which the authors suggest explains lower recognition — [Sato et al. 2022, Frontiers in Psychology](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2021.800657/full)
- Skin thickness (Morpheus, 2025, tendon-driven animatronic face): 2 and 2.5 mm skins gave unnaturally localized deformation around pasted regions; 4 mm gave smooth, natural movement; 5 mm was too stiff and significantly limited visible deformation (qualitative visual comparison) — [Morpheus, arXiv 2507.16645](https://arxiv.org/pdf/2507.16645)
- Affetto child android: the distribution of surface displacements depends largely on the uneven curvature, thickness and elasticity of the skin sheet; the team measured 116 surface points against actuator inputs — [Ishihara et al. 2018, Frontiers in Robotics and AI](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2018.00119/pdf)
- A review of android faces notes skin thickness, material and elasticity affect overall movement, and friction between skin and shell also matters — [PMC review](https://pmc.ncbi.nlm.nih.gov/articles/PMC8019968)
- Timing matters and is tunable on a preview: Nikola Study 3 showed 24 videos (6 emotions x 4 speeds, neutral-to-apex in 250, 500, 1,000, 2,000 ms); speed had a significant main effect (F(1.52, 44.14) = 12.62, p < .001) and an emotion x speed interaction; faster was more natural overall, surprise got less natural as it slowed, sadness more natural when slower — [Sato et al. 2022](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2021.800657/full)

### Inferences
- Fidelity ladder for Frank (effort is my estimate):
  1. 2D schematic face in the existing localhost page (canvas/SVG: eye discs that translate, lid arcs whose opening follows lid angle, brow polylines from the four brow servos, jaw drop and lip/corner lines). Same joint dict as the Pico stream. About half a day to a day. Enough to tune sequencing, gaze, blink timing, blend weights and emotion dynamics; this is where most tuning time should go.
  2. 3D twin in the browser: three.js + STLLoader (or a small URDF written by hand and `urdf-loader`) using meshes already exported by `cad/` (eyeballs, lids, jaw, brow links), each mesh parented to a pivot whose angle is the servo angle through the same linkage maths as `browgeom.py`. About 2 to 4 days, mostly pivot/linkage plumbing. Adds silhouette and eyelid/eyeball occlusion checks; still no skin.
  3. Blender + the Servo Animation add-on: best if the makers want to keyframe in a full animation tool and also drive the head live; GPL-3.0 add-on, Arduino-side library would need porting to the Pico protocol (or a small Python bridge reading its JSON export). 1 to 3 days to rig.
  4. PyVista desktop preview: fastest from Python and build123d STLs, but duplicates the browser UI; use only if a Python-only window is preferred.
- What does not transfer, and the cheap compensations: (a) servo lag and slew limit: run the preview through a first-order lag plus dead time and a max deg/s per joint measured on the real servos (Q5), so the preview shows what the head can actually do; (b) skin damping: the skin reduces and smooths visible amplitude, especially at mouth corners and brow, so expect to need larger servo excursions on the real head than look right on the preview; keep a per-joint "skin gain" table set during real-head confirmation; (c) backlash/deadband: invisible on screen; small, slow micro-motions (breathing, saccade drift) need checking on hardware; (d) silicone drag can change the neutral pose (skin pulls the jaw/lids), so the head's neutral is a measured calibration, not a CAD value.
- Treat the preview exactly like EA/Furhat do: the engine emits one joint frame per tick; the transport sink is "Pico", "preview" or both. Never let the preview have its own animation code path.

## 2. Record and replay: logging joints and events, replaying onto preview or head, scrubbing, formats

### Takeaway
The simplest proven format is a timestamped JSON trajectory with a sidecar audio file (Pollen's Reachy Mini emotion library), played back by time-based interpolation rather than by frame index. For Frank, log every tick as JSON Lines (one object per tick with all joints plus engine state and events), keep audio as WAV beside it, and replay through the same output sinks; use Rerun (MIT/Apache-2.0) if a ready-made scrub timeline is wanted.

### Cited Findings
- Reachy Mini recorded move JSON keys: `"description"`, `"time"` (list of float timestamps), `"set_target_data"` (one dict per sample with `"head"` as a 4x4 pose, `"antennas"` in radians, optional `"body_yaw"` defaulting to 0.0); `evaluate(t)` finds neighbours with `bisect.bisect_right` and linearly interpolates (`lerp`) antennas and body yaw, with a pose interpolation for the head; audio is a sidecar file with the same stem, `.wav` tried first — [reachy_mini recorded_move.py](https://raw.githubusercontent.com/pollen-robotics/reachy_mini/main/src/reachy_mini/motion/recorded_move.py)
- `RecordedMoves` loads a library from a Hugging Face dataset and uses the local cache only "to avoid blocking network calls during playback"; a Move's `evaluate(t)` is "typically called at a high-frequency (eg. 100Hz)" — [Reachy Mini Motion API docs](https://huggingface.co/docs/reachy_mini/main/API/motion.md)
- Pollen's emotions library stores each emotion as `<emotion>.json` plus `<emotion>.wav` at the dataset root; played with `RecordedMoves` / `play_move` (search extract) — [HF dataset: pollen-robotics/reachy-mini-emotions-library (mirror)](https://huggingface-proxy-6ci.pages.dev/datasets/pollen-robotics/reachy-mini-emotions-library)
- Sampling rate conflict: the brief mentions 50 Hz clips, but Pollen's Marionette recorder captures encoder data and FK poses "at 100 Hz", and the SDK docs say ~100 Hz evaluation; no source found for 50 Hz — [Marionette recorder](https://pollen-robotics-marionette.static.hf.space/index.html); [Reachy Mini Motion API](https://huggingface.co/docs/reachy_mini/main/API/motion.md)
- Library size differs between sources (81 vs 138 motions), probably versions (search extract) — [reachy-mini-mcp server.py (glama)](https://glama.ai/mcp/servers/@jackccrawford/reachy-mini-mcp/blob/f1588c6d49dd6866590080163b447434b2bce863/src/server.py); [RemiFabre emotions app](https://remifabre-emotions.static.hf.space/index.html)
- Blender Servo Animation exports "Animation Servo Positions" as `.h` (Arduino/C++ header), `.json` (generic) and `.bin` (for SD card) — [GitHub: blender-servo-animation](https://github.com/timhendriks93/blender-servo-animation)
- Bottango: keyframe timeline with interpolation curves; by default needs a live USB connection with the computer acting as server; "Arduino Mode" (File > Export for Arduino Mode) generates an `.ino` plus `lib/` folder for standalone playback; other microcontrollers can implement the Bottango API (third-party tutorials) — [Adafruit: Animating Animatronics](https://learn.adafruit.com/animating-animatronics?view=all); [KevsRobots: Arduino Mode](https://dcmpx.remotevs.com/com/kevsrobots/www/PL/learn/bottango/09_arduino_mode.html); [DigiKey: Getting started with Bottango](https://www.digikey.com/en/maker/tutorials/2024/how-to-get-started-with-bottango)
- Adafruit's Feedback-Servo-Record-and-Play sketch records motion data from feedback servos to EEPROM and plays it back on a button press — [Core Electronics: Analog Feedback Servo](https://core-electronics.com.au/analog-feedback-servo.html)
- Rerun: "SDK for logging computer vision and robotics data paired with a visualizer for exploring that data over time"; licence MIT OR Apache-2.0 — [GitHub: rerun-io/rerun](https://github.com/rerun-io/rerun); [conda-forge rerun-sdk](https://anaconda.org/conda-forge/rerun-sdk)
- Rerun timeline: "Scrub through simulation history like a video" (third-party tutorial) — [RoboVerse: Rerun visualization](https://roboverse.wiki/metasim/get_started/quick_start/17_rerun_visualization)
- EA's Virtual Robot timelines carry robot motion, audio and speech items on one timeline (search extract) — [EA wiki: Virtual Robot](https://wiki.engineeredarts.co.uk/Virtual_Robot)

### Inferences
- Recommended Frank log format (`.jsonl`, one line per tick, 25 to 50 lines/s): `{"t": <monotonic s>, "seq": n, "joints": {"eye_x": .., "lid_UL": .., ...}, "cmd": {...pre-limit values...}, "state": {"emotion": .., "valence": .., "arousal": .., "speaking": true}, "events": [{"type": "tag", "value": "[smirk]"}, {"type": "utterance_start", "id": ..}]}`, plus one header line with schema version, joint list, limits and calibration hash. Write audio (TTS output and mic) as WAV with the same stem and the audio start time in the header. JSONL survives crashes (each line stands alone) and is trivial to grep and load with pandas. At 50 Hz x ~20 joints this is ~50 to 100 MB per hour uncompressed; gzip at rotation.
- Log both the commanded value after the engine (pre-limit) and the value actually sent (post-limit, post-rate-limit); the difference shows when the safety layer is fighting the animation.
- Replay = read the file, evaluate by time (like Reachy's bisect + lerp) and push through the same sink as live. Replay onto the preview first, then onto the head with a speed scale (0.5x) for risky clips.
- Clips (authored or recorded expressions) can use the Reachy-style shape: `{"description", "time": [...], "frames": [{joint: angle}], "fps_hint"}` + optional WAV. Keep clip angles in "engine units" (normalized -1..1 per joint or degrees before calibration) so clips survive a servo swap.
- Scrubbing: cheapest is a range slider in the existing localhost page that seeks the log and pushes frames to the 2D/3D preview; Rerun is the zero-UI-work alternative (log joints as scalars, events as text, preview frames as transforms) and works on Windows and macOS.
- Effort: logger 2 to 4 hours; replay CLI 2 to 4 hours; browser scrub page about 1 day; Rerun integration about half a day.

## 3. Live tuning: parameter UIs, hot-reload, A/B, presets, game-feel practice

### Takeaway
Game-feel practice says build a dedicated test environment where every tunable variable is exposed and can be changed while the system runs; for Frank the cheapest fit is a browser panel (Tweakpane, MIT) on the existing localhost page talking WebSocket to the engine, backed by a parameter file the engine hot-reloads, with named presets and an A/B toggle.

### Cited Findings
- Swink breaks game feel into input, response, context, polish, metaphor and rules, and recommends building a test environment for the variables you will later tune — [Game Developer: Game Feel - The Secret Ingredient](https://www.gamedeveloper.com/game-platforms/feature-game-feel---the-secret-ingredient-)
- Pichlmair and Johansen's survey separates tuning (shaping the physicality of objects for cohesion and predictability) from juicing (polish amplification for feedback clarity) — [Designing Game Feel: A Survey](https://pure.itu.dk/en/publications/designing-game-feel-a-survey/); [arXiv 2011.09201](https://arxiv.org/pdf/2011.09201)
- The Squeezer research tool lets designers edit juice effect sequences while the game runs, shortening iteration times; supports runtime manipulation of effect descriptions — [core.ac.uk: Squeezer](https://core.ac.uk/download/362610511.pdf)
- Tweakpane: "a compact pane library for fine-tuning parameters and monitoring value changes, inspired by dat.GUI"; dependency-free; MIT licence — [GitHub: cocopon/tweakpane](https://github.com/cocopon/tweakpane); [npm tweakpane](https://www.npmjs.com/package/tweakpane)
- trame-tweakpane is an MIT Python wrapper for Tweakpane — [PyPI trame-tweakpane](https://pypi.org/project/trame-tweakpane)
- Dear PyGui: MIT; draws widgets on the GPU (DirectX 11 on Windows, Metal on macOS, OpenGL3 on Linux); built on Dear ImGui with ImPlot; `dpg.add_slider_float(...)`; version 2.3.1 on PyPI with wheels for CPython 3.12 to 3.14 — [GitHub: hoffstadt/DearPyGui](https://github.com/hoffstadt/DearPyGUI); [PyPI dearpygui 2.3.1](https://pypi.org/project/dearpygui/2.3.1/)
- Controller-side rate limiting as a tunable: the Pololu Maestro "speed" setting caps output change in units of 0.25 us per 10 ms and acceleration ramps speed up and down; the speed limit "will not help your servo go faster than what it is physically capable of" — [Pololu Maestro: serial servo commands](https://www.pololu.com/docs/0J40/5.e)
- Blender Servo Animation's live mode exposes a per-servo "Threshold" (max allowed change between frames) and sends large jumps in small increments — [GitHub: blender-servo-animation](https://github.com/timhendriks93/blender-servo-animation)

### Inferences
- Recommended: one `face_params.yaml` (or JSON) holding every engine constant (blink interval distribution, saccade amplitude/rate, emotion attack/decay time constants, blend weights per emotion, per-joint gain/offset, lip-sync gain and lead). The engine watches its mtime each second and reloads atomically (parse to a new object, validate ranges, swap; on parse error keep the old one and show the error in the page). This gives hot reload from any editor with zero UI work.
- On top, a Tweakpane panel in `web.html` bound to the same schema: sliders send `{"set": {"blink.mean_s": 4.2}}` over WebSocket; the engine applies it live and echoes back the full state so two makers on two laptops see the same values. "Save preset as..." writes a named YAML; "A/B" holds two parameter sets and toggles every N seconds or on a key, ideally with the same replayed conversation log (Q2) so only the parameters differ.
- Add "audition" buttons: trigger each emotion, each tag, a blink, a saccade, a 10 s idle, so tuning does not depend on having a live conversation.
- Dear PyGui is the better choice only if a native window with fast plots (servo command traces) is wanted; Tkinter sliders already exist in the project and are fine for raw pose setting but awkward for 50+ parameters.
- Effort: hot-reload 2 to 4 hours; Tweakpane panel generated from the schema about 1 day; preset save/A-B about half a day.

### Gaps
- Found no published workflow from a robotics company describing its live-tuning UI for facial expression dynamics; the game-dev literature is the closest practice source.

## 4. Authoring by puppeteering: webcam blendshapes to servos, filtering, per-servo calibration

### Takeaway
MediaPipe Face Landmarker (Apache-2.0 code, Python, 52 ARKit-style blendshapes plus a head transform) is the standard free way to capture a maker's own expressions; Furhat ships the same idea with iPhone ARKit capture into editable JSON gestures. Map each blendshape (or a small linear combination) to each servo through a per-servo calibrated range, smooth with the 1 Euro filter, record as clips, then edit; a learned mapping (Morpheus-style self-model) is the research version and not needed here.

### Cited Findings
- MediaPipe Face Landmarker predicts "52 blendshape scores"; running modes IMAGE, VIDEO and LIVE_STREAM; options `output_face_blendshapes` (default False), `output_facial_transformation_matrixes` (default False), `num_faces` (default 1; smoothing applies only when set to 1); model bundle `face_landmarker.task`; Android, iOS, Python and Web; code samples Apache 2.0, content CC BY 4.0; no latency benchmarks on the page — [MediaPipe Face Landmarker guide](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)
- A KDDI workflow pulled 52 blendshapes in real time from a performer to drive virtual humans — [Google Developers Blog, July 2023](https://developers.googleblog.com/2023/07/mediapipe-enhancing-virtual-humans-to-be-more-realistic.html)
- A MediaPipe issue thread notes the face mesh is not invariant to head orientation, making AR puppeteering results hard to reproduce; one commenter found the older landmark path had better temporal coherence (less jitter) (search extract) — [GitHub: mediapipe issue 2526](https://github.com/google-ai-edge/mediapipe/issues/2526)
- Left/Right in blendshape names refer to the subject's face; passing a horizontally mirrored image inverts them (search extract; source page not confirmed, verify in testing) — [GitHub: mediapipe issue 2526](https://github.com/google-ai-edge/mediapipe/issues/2526)
- Kalidokit solves MediaPipe landmarks into blendshapes and rotations for avatars/VTubing; its FaceSolver takes MediaPipe results directly — [Kalidokit (docsearch)](https://docsearch.algolia.com/mcp/docs/repo/yeemachine/kalidokit)
- Furhat Gesture Capture: record a facial performance with iPhone X or later, edit speed/amplitude, export JSON into the skill's resource folder (search extract; blog URL malformed) — [Furhat SDK](https://www.furhatrobotics.com/furhat-sdk)
- Furhat notes it "can be tedious and difficult to define new convincing gestures procedurally" (search extract) — [PyPI expressive-furhat](https://pypi.org/project/expressive-furhat/)
- 1 Euro filter: speed-based low-pass that reduces jitter when slow and lag when fast; parameters fcmin (mincutoff, > 0) and beta; tuning: "First beta is set to 0 and fcmin (mincutoff) to a reasonable middle-ground value such as 1 Hz", adjust fcmin to remove jitter while holding still, then raise beta during fast moves, starting with "values like 0.001 or 0.0001"; rule: "if high speed lag is a problem, increase beta; if slow speed jitter is a problem, decrease fcmin"; Casiez, Roussel, Vogel, CHI '12, pp. 2527-2530; verified Python implementation, BSD licence — [1 Euro Filter page](https://gery.casiez.net/1euro/)
- Morpheus: a self-modeling network learns motor actions -> facial landmarks; gradient backprop links each expression's blendshape coefficients to motor signals; a separate network maps speech to blendshapes; hardware and software released on GitHub (licence not stated in abstract) — [Morpheus, arXiv 2507.16645](https://arxiv.org/abs/2507.16645)
- Pollen's Marionette: "disables torque to give you full manual control"; move the head by hand; records encoder data and FK poses at 100 Hz after a 3-2-1 countdown; optional sound; replay and refine before export; saves JSON + WAV — [Marionette recorder](https://pollen-robotics-marionette.static.hf.space/index.html)
- Bottango supports live recording of gamepad puppeteering that converts to editable keyframes — [KevsRobots: Bottango with a gamepad](https://dcmpx.remotevs.com/com/kevsrobots/www/PL/learn/bottango/10_use_with_gamepad.html)
- Analog feedback servos: a fourth wire brings out the potentiometer wiper so position can be read on an analog input "while still driving the servo as normal"; the standard-size Adafruit model moved to digital internal control on 29 Jan 2024 with the analog feedback unchanged — [Core Electronics: Analog Feedback Servo](https://core-electronics.com.au/analog-feedback-servo.html); [Adafruit 1449](https://www.adafruit.com/products/1449)
- Blender Servo Animation per-servo calibration: Position Min/Max where the servo physically stops, Neutral Angle, Rotation Range (typically 180); a "Calibrate servo" dialog (requires live connection) where you adjust min/max "until the servo stops moving"; the servo moves at full speed during calibration and jump handling is not applied — [GitHub: blender-servo-animation](https://github.com/timhendriks93/blender-servo-animation)

### Inferences
- Pipeline for Frank (about 1 to 2 days; MediaPipe is already a project dependency):
  1. `capture.py`: webcam -> Face Landmarker LIVE_STREAM with `output_face_blendshapes=True` and `output_facial_transformation_matrixes=True` -> per-channel 1 Euro filter -> mapping -> engine "puppet" input -> preview and/or head.
  2. Mapping table (YAML): `jaw <- jawOpen`; `lid_U* <- 1 - eyeBlink*` (with eyeWide* adding opening); `eye_x <- eyeLookOut/In*`, `eye_y <- eyeLookUp/Down*`; brow inner <- `browInnerUp`, brow outer <- `browOuterUp*`, brow down <- `browDown*`; mouth corners <- `mouthSmile*` minus `mouthFrown*`; lips <- `mouthPucker`, `mouthFunnel`, `mouthRollUpper/Lower`, `mouthUpperUp*`/`mouthLowerDown*`. Each target is `clamp(offset + gain * sum(w_i * bs_i))` in normalized units, then through the servo calibration. Head yaw/pitch from the transform matrix can feed eye gaze or be ignored.
  3. Per-performer calibration: record 3 s neutral and 3 s of each extreme ("eyes wide", "full smile", "brows up", "jaw open") and normalize each blendshape to that person's 0..1; raw MediaPipe scores differ by face, lighting and glasses.
  4. Per-servo calibration (already partly in the slider windows): min, max, neutral, direction, and a measured "visible range on skin". Keep calibration separate from clips so a replaced servo only needs recalibration.
  5. Record mode writes clips in the Q2 format; a "pose snapshot" key saves the current mapped frame as a named pose for the emotion library.
- Expect mirroring confusion: decide once whether the maker acts "as Frank" (mirror) or "facing Frank", and test with a one-sided wink.
- The Marionette approach (move the face by hand, record) needs position feedback; with stock MG90S servos it is only possible after soldering a wire to each pot wiper (Lars has a soldering iron, no drill) or using feedback servos. Worth it for the brow and lips where hand-shaping on the real skin is more natural than a webcam.

- MediaPipe Python latency on a typical laptop was not found in official docs.
- Licences of Kalidokit and Morpheus code not verified.

## 5. Measuring the real servo response: latency, speed, identification, lag compensation

### Takeaway
Hobby servos are open loop to the user, so teams measure them externally: slow-motion video with a visible command marker, an IMU on the horn, or tapping the pot wiper with an ADC/logic analyzer; the result is a simple model (dead time + slew-rate limit + first-order lag, plus deadband) per joint, used both to make the preview honest and to lead the commands (send earlier) where timing matters, mainly lip sync.

### Cited Findings
- An SG90 characterization (not peer reviewed) fixed an IMU to the horn to measure shaft angle and states "the servo is, for the user, an open loop system"; the servo lags the input in step tests and results vary with centre point and input (nonlinearity) (search extract) — [Scribd: SG90 Characterization](https://www.scribd.com/document/964040407/SG90-Characterization)
- COBEM 2021 (MG995): with no position feedback, the authors fitted a transfer function from step responses at several amplitudes and validated it with a nonlinear simulation including voltage saturation (search extract) — [ABCM COBEM 2021 paper 0636](https://abcm.org.br/proceedings/view/COB2021/0636)
- Paparazzi's servo tester suggests opening the servo and measuring the pot voltage "with a high speed recorder device", e.g. a logic analyzer with analog inputs — [Paparazzi docs: servo tester](https://docs.paparazziuav.org/v5.18/module__servo_tester.html)
- Slow-motion video at about 120 fps with frame counting to get angular velocity; first-order model plus pure delay; typical dead time 5 to 20 ms; +/-10 % move-time tolerance (vendor SEO content, unverified numbers) — [kpower.com insight 7401](https://www.kpower.com/insight_bldc/7401.html); [kpower.com insight 7415](https://www.kpower.com/insight_servo/7415.html)
- Analog feedback servos expose the wiper for reading position as a voltage — [Core Electronics: Analog Feedback Servo](https://core-electronics.com.au/analog-feedback-servo.html)
- A full-size vehicle steering study handled actuator deadband by remapping commands around the deadband limits (different domain, same technique) — [arXiv 1708.07771](https://arxiv.org/pdf/1708.07771)
- Pololu: speed limits cannot make a servo faster than it physically is; supply voltage and load also limit speed — [Pololu Maestro: serial servo commands](https://www.pololu.com/docs/0J40/5.e)

### Inferences
- Cheap protocol per joint (about half a day for all joints, phone only):
  1. Put an LED on a Pico GPIO in the camera frame, plus a printed protractor or tape marks behind the horn/eyeball/lid. Firmware lights the LED on the same tick it changes the PWM target.
  2. Command steps of 5, 20, 60 deg and back, with and without skin, at the real supply voltage. Film at 240 fps (most phones) or 120 fps.
  3. Count frames from LED-on to first motion (dead time; 1 frame = 4.2 ms at 240 fps), and to 90 % of travel (gives slew rate in deg/s). Small steps reveal deadband (commands that produce no motion).
  4. Repeat end-to-end from the laptop: flash a patch on the laptop screen in frame at the moment the engine emits the frame; the LED-to-motion delay is the servo, the screen-to-LED delay is USB/serial + Pico tick.
- Alternative without video: solder a wire to one MG90S pot wiper and read it with a Pico ADC at 1 kHz; one sacrificial servo per servo type is enough to identify the model; also gives stall detection (Q7).
- An IMU on the horn works for the large eye/jaw servos but adds mass on small lid servos.
- Use: (a) preview applies the per-joint model (dead time, max deg/s, first-order tau); (b) the engine sends mouth/jaw frames early by the measured mechanical delay (lead), which matters because lip sync is judged against audio; gaze and brows rarely need lead; (c) keep commanded speeds below the measured max so the servo never saturates (saturation is where lag becomes variable).
- Re-measure with skin on: silicone adds load and changes both speed and resting position.

### Gaps
- No reliable published latency/speed figures for MG90S under load were found in this session (datasheets quote no-load speed only); the project should measure its own.
- No peer-reviewed protocol specific to animatronic servo identification was found.

## 6. Evaluating expressions with small samples: methods, scales, how HRI papers do it, pitfalls

### Takeaway
HRI face studies typically use 30 to 90 people with a forced-choice label task (6 or 7 basic emotions), sometimes plus Godspeed or naturalness ratings; with 10 to 30 people the useful, defensible version is: short video clips, a modified forced choice that includes a "none of these / other" option (or free labels first), randomized order, no context, then a separate in-context check, and per-expression hit rates against chance. Labels prime answers, context shifts readings strongly, and silicone skin weakens intensity, so recognition should be checked on the real skinned head.

### Cited Findings
- Bennett and Šabanović used "the same 7-option forced-choice design ... as was used in studies with Kismet, Eddie, etc." on a minimalist robot face and a digital avatar, and administered NARS and Godspeed; the IJSR 2014 version had n = 75; adding neck motion raised identification to 100 % for all expressions except fear (search extract) — [Bennett & Šabanović HRI 2013](https://homes.luddy.indiana.edu/selmas/BennettSabanovic-HRI2013.pdf); [Bennett & Šabanović IJSR 2014](https://homes.luddy.indiana.edu/selmas/BennettSabanovic-IJSR2014.pdf) (DOI 10.1007/s12369-014-0237-z)
- Sato et al. 2022 (Nikola android): Study 1 used a single certified FACS coder (no participant sample) who found 17 AUs produced; Study 2: 30 adults (a priori power analysis required 23), six photographs, six-label forced choice, each image twice (12 trials), two practice trials, no time limit, no feedback; all emotions above the 16.7 % chance level; happiness 90.0 %; surprise, sadness and happiness better than disgust, fear and anger; Study 3: 30 adults (power analysis 24), 24 videos, 7-point naturalness scale, replays allowed — [Sato et al. 2022](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2021.800657/full)
- Sato et al. note earlier android studies had not shown significantly high recognition of disgust and fear (search extract) — [Sato et al. 2022 (PDF)](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2021.800657/pdf)
- An online study compared emotion recognition across a human, a human-looking robot and a mechanical-looking robot; participants chose one of 7 emotions as radio buttons under each video — [arXiv 2410.14337](https://arxiv.org/pdf/2410.14337)
- Russell (1994) criticized the forced-choice "standard method": it restricts options and can force selection of an incorrect name if the best one is absent; when "anger" is not offered, observers instead agree the same face shows contempt, frustration or disgust — [Psychonomic/Springer PDF](https://link.springer.com/content/pdf/10.3758/BF03200822.pdf); [PubMed 8165272](https://pubmed.ncbi.nlm.nih.gov/8165272/)
- Frank and Stennett concluded the modified forced-choice format (adding a "none of these terms" option) appears to remedy the artifactual agreement; Nelson and Russell (2016) showed with a novel nonsense-expression foil that some label-matching tasks produce "illusory recognition"; a 2013 study argued forced choice may still reflect recognition adequately, so the debate is unresolved — [Frontiers in Psychology 2014 review](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2014.00555/pdf); [QxMD: effect of forced choice vs open verbal classification](https://read.qxmd.com/read/23798981/the-effect-of-forced-choice-on-facial-emotion-recognition-a-comparison-to-open-verbal-classification-of-emotion-labels)
- Context: Zhang's Sheffield PhD found observers' judgments of a mechanical robot head's expressions (servo parameters set from FACS) were shifted by surrounding emotional context (BBC News clips, affective pictures, classical music, film clips) — [Zhang 2013, White Rose eTheses](https://etheses.whiterose.ac.uk/id/eprint/3809/)
- Bennett and Šabanović (2015, Interaction Studies, 93 participants): context effects could override cultural differences, most notably for fear — [Interaction Studies 16(2)](https://www.jbe-platform.com/content/journals/10.1075/is.16.2.11ben)
- Bennett, Šabanović, Fraune and Shaw (n = 48): context congruency significantly affected perception, varying with valence, regardless of participants' culture (aggregator listing only) — [akademskiimenik listing](https://www.akademskiimenik.ba/publikacije/fc8b9805067858a66c7686e294d2b1cdb686b9bd)
- In social context, people do not mirror an android's expressions but react to their informational value — [Frontiers in Neurorobotics 2018](https://www.frontiersin.org/journals/neurorobotics/articles/10.3389/fnbot.2018.00014/pdf)
- Godspeed Questionnaire Series (Bartneck et al. 2009, IJSR): five scales (anthropomorphism, animacy, likeability, perceived intelligence, perceived safety), 24 semantic-differential items on 1-5; "Artificial - Lifelike" appears in both anthropomorphism and animacy; Ho and MacDorman argue the anthropomorphism index may conflate interpersonal warmth; one of the most used HRI questionnaires; translations include German and Dutch; Polish validation Cronbach's alpha 0.90 overall — [Bartneck: Godspeed 2009](https://www.bartneck.de/publications/2009/measurementInstrumentsRobots/); [GMU HRI Scale Database: Godspeed](https://hriscaledatabase.psychology.gmu.edu/attitudes/attributes/2024/10/31/Godspeed.html); [Weiss & Bartneck 2015 meta-analysis](https://www.bartneck.de/publications/2015/metaAnalysisGodspeedQuestionnaire/index.html); [Tobis et al. 2023](https://www.citedrive.com/en/discovery/the-godspeed-questionnaire-series-in-the-assessment-of-the-social-robot-tiago-by-older-individuals/)
- Self-Assessment Manikin (Bradley and Lang 1994, J. Behav. Ther. Exp. Psychiatry 25(1):49-59): non-verbal pictorial ratings of valence, arousal and dominance; usually a 9-point scale (some secondary sources say 5) — [Wikipedia: SAM](https://en.wikipedia.org/wiki/Self-Assessment_Manikin); [PMC5808109](https://pmc.ncbi.nlm.nih.gov/articles/PMC5808109); [Penn State Psych 425: measuring emotions](https://psu.pb.unizin.org/psych425/chapter/measuring-emotions/)
- Skin weakens recognisability: Nikola's weaker-than-human intensity is the authors' explanation for lower recognition — [Sato et al. 2022](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2021.800657/full)

### Inferences
- Small-sample protocol for Frank (10 to 20 people, 10 minutes each; my design, built from the methods above):
  1. Stimuli: 2 to 4 s video clips of the real skinned head (neutral -> apex -> hold), filmed once, same framing and lighting; also the same clips rendered from the preview to see what transfers. Include 1 or 2 deliberately ambiguous/"nonsense" expressions as foils (Nelson & Russell).
  2. Free label first ("What is Frank feeling? one or two words"), then modified forced choice with the target set (e.g. happy, sad, angry, surprised, afraid, disgusted, sly/smug, bored) plus "none of these", then a 1-7 intensity and a SAM valence/arousal pick. Randomize clip order per person; no feedback.
  3. Score: hit rate per expression with a binomial test against chance (1/k for k options); with n = 15 and 9 options (chance 11 %), 6 of 15 correct is already p = 0.004 and 5 of 15 is p = 0.02 (one-sided binomial, computed here), so small samples can show "readable vs not", not fine differences. Also build a confusion matrix: which expression is read as which tells you what to change (e.g. brows).
  4. Context pass: the same clips inside a short scripted line of dialogue; if readings flip, the expression relies on context and is fine in conversation but not as a standalone tell.
  5. Optional: Godspeed (24 items) once at the end of a live chat if the team wants to compare personality versions; it is long for an open day.
- Open-day/hackathon version: a "guess Frank's mood" card with 6 to 8 pictograms plus "something else", tally marks per expression on a sheet or a phone form; play each expression in random order from a replay file; also have people pick the expression from a menu and score "did Frank do what you asked" (reverse task). Expect fear and disgust to score worst (Sato; Bennett); Frankenstein's character will make "angry" over-read.
- Pitfalls to design around: labels prime answers (add "none of these", ask free labels first); context changes readings (test both with and without); order effects (randomize); the skin damps motion (test only on the skinned head, at the final speed); a moving neck/gaze helps recognition (Bennett), so decide whether clips include gaze; the makers cannot be raters; show people the neutral pose first so the resting Frankenstein scowl is not read as anger.
- Tools: a page in the existing localhost app that plays clips in random order and logs answers to JSONL; or a free form tool. Effort: about 1 day.

### Gaps
- Could not extract the full text of Bennett & Šabanović IJSR 2014 (PDF text not extractable here), so their exact per-emotion rates and timing details are unverified.
- No source found on minimum sample sizes specific to robot-face recognition beyond the power analyses reported by Sato et al. (23 to 24 required, 30 used).

## 7. Safety and robustness tooling: soft limits, watchdogs, safe pose, rate limits, stall/brown-out detection

### Takeaway
Commercial servo controllers implement exactly the pattern Frank needs: a serial timeout that sends channels to defined "home" positions, with speed/acceleration limits applied to that move, plus readable error flags. On the Pico this is a host-heartbeat timeout in firmware (safe pose, slew-limited), a hardware watchdog for firmware hangs, per-joint soft limits and slew limits in both laptop and Pico, and host-side monitoring of acks; stall and brown-out detection need a current or voltage sense that the sources did not cover.

### Cited Findings
- Pololu Maestro serial timeout: resolution 0.01 s, maximum 655.35 s, "A timeout period of 0.00 disables the serial timeout error"; it fires when no valid serial command arrives in the period; it exists so "servos and digital outputs go back to their default states" when the controlling software stops working — [Pololu Maestro: serial settings](https://www.pololu.com/docs/0J40/5.a)
- Maestro per-channel "On startup or error": Off, Ignore or Go to (a set position); the output "will smoothly transition to the specified position on an error, but not during start-up"; speed in units of 0.25 us / 10 ms, acceleration in 0.25 us / 10 ms / 80 ms — [Pololu Maestro: channel settings](https://www.pololu.com/docs/0J40/4.b)
- Maestro reports serial signal and overrun errors; a "Get errors" command returns and clears the error bits; one user saw the error light and servos stop above ~12 commands/s in their setup (forum anecdote) — [Pololu forum: command rate](https://forum.pololu.com/t/micro-maestro-command-rate/6557); [Maestro manual p.44](https://www.manualsdir.com/manuals/570384/pololu-maestro.html?page=44)
- MicroPython `machine.WDT(id=0, timeout=5000)` (ms); RP2040 maximum 8388 ms; "Once it is running the timeout cannot be changed and the WDT cannot be stopped either"; call `feed()` only after confirming everything works — [MicroPython machine.WDT](https://docs.micropython.org/en/latest/library/machine.WDT.html)
- Blender Servo Animation warns to set Neutral Angle carefully because "the servo first moves to its natural neutral when powered"; starting live mode immediately sends the current frame so servos may jump; its Threshold limits per-frame change and large jumps are sent in small increments — [GitHub: blender-servo-animation](https://github.com/timhendriks93/blender-servo-animation)
- EA's "Limit Control" restricts which body parts a sequence may drive (arbitration between sources) (search extract) — [EA wiki: Virtual Robot](https://wiki.engineeredarts.co.uk/Virtual_Robot)
- Adafruit analog feedback servos allow reading actual position while driving (basis for stall detection: commanded vs measured) — [Core Electronics: Analog Feedback Servo](https://core-electronics.com.au/analog-feedback-servo.html)

### Inferences
- Layers for Frank (firmware about 1 day, host about half a day):
  1. Pico, per joint: hard clamp to the mechanical cap (from the pose sweeps, PLAN docs), soft limit below it, max deg/s slew and optional max accel; applied to every target regardless of source. Keep the numbers in one table generated from `params.py`/calibration so laptop and Pico agree.
  2. Pico heartbeat: every frame carries a sequence number; if no valid frame for e.g. 300 ms, ramp (slew-limited, like Maestro's "smoothly transition") to a safe pose: eyes centred, lids half closed, jaw closed against skin but not pressing, brows neutral; after a further few seconds, optionally detach PWM on servos whose safe pose holds without torque, to stop buzzing and heat.
  3. Hardware watchdog on the Pico (`machine.WDT`, e.g. 1 to 2 s, under the 8388 ms max) fed only from the main loop after the servo update; boot code must ramp from the measured neutral, not jump (servos snap to their own neutral at power-up).
  4. Laptop: the engine is the only writer; any tool (sliders, puppet, replay) goes through an arbiter with per-joint ownership (EA's Limit Control idea), so a crashed tool cannot leave a joint at full deflection.
  5. Host-side health: the Pico replies with a small status at 5 to 10 Hz (last seq, loop time max, timeout count, reset cause, supply voltage if measured). The host flags missing acks, rising loop time, or watchdog resets in the web page and in the JSONL log.
  6. Stall/brown-out (needs hardware): a Pico ADC on a divider from the servo rail to log sag during big moves; optionally an INA219-type current sensor on the rail; or one pot-wiper wire per critical joint (jaw, lids) to compare commanded vs actual and cut torque on sustained mismatch. Brown-outs often show as Pico resets, so the reset-cause report in step 5 is the first, free detector.
- "Rehearsal mode" when the head is not on the bench: engine runs with the preview sink only; when the head is attached, a "dry run at 50 % amplitude and 50 % speed" switch is the first thing used after any servo swap.

### Gaps
- No source found in this session on detecting hobby-servo stalls or brown-outs from the host side, or on rail-sag figures for MG90S arrays; the measures above are engineering practice, not sourced findings.
- Exact Maestro error-bit name for serial timeout was not confirmed.

## 8. What should this team build, in what order (recommendation)

### Takeaway
Build one engine that emits joint frames to interchangeable sinks (Pico, 2D preview, 3D preview, JSONL log), then add tooling in this order: logger + replay, 2D preview in the existing localhost page, hot-reload params + Tweakpane panel with presets/A-B, firmware safety layer, servo measurement and a lag model in the preview, MediaPipe puppeteer capture, 3D three.js twin, and a 10 to 20 person recognition test on the skinned head.

### Cited Findings
- Professional twins share the control values and timeline with the real robot (EA Virtual Robot/Tritium Animator, Furhat virtual robot) — [EA wiki: Virtual Robot](https://wiki.engineeredarts.co.uk/Virtual_Robot); [Furhat SDK](https://www.furhatrobotics.com/furhat-sdk)
- Pollen's open format (timestamped JSON + WAV, time-interpolated playback) is a proven minimal clip format — [reachy_mini recorded_move.py](https://raw.githubusercontent.com/pollen-robotics/reachy_mini/main/src/reachy_mini/motion/recorded_move.py)
- Tools and licences: Tweakpane MIT ([GitHub](https://github.com/cocopon/tweakpane)); Dear PyGui MIT ([GitHub](https://github.com/hoffstadt/DearPyGUI)); Rerun MIT/Apache-2.0 ([GitHub](https://github.com/rerun-io/rerun)); MediaPipe code Apache 2.0 ([guide](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)); 1 Euro filter Python BSD ([page](https://gery.casiez.net/1euro/)); Blender Servo Animation GPL-3.0 ([GitHub](https://github.com/timhendriks93/blender-servo-animation))

### Inferences
